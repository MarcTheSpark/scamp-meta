# cb2 → clockblocks 1.0: release mechanics + test-status reconciliation

Written 2026-06-16. Captures the plan for turning `cb2/` into clockblocks 1.0 (now recorded in `cb2/PLAN.md`
under **Release mechanics**), plus a reconciliation of the PLAN's status against the actual code.

## The git wrinkle (why "make cb2 the 1.0 branch" isn't a branch op)

- `cb2/` is its **own independent git repo** (`main`, no remote) carrying the Step-1..15 redesign history.
- The published `clockblocks/` is a **separate repo**: v0.6.10, remotes `origin` (GitHub `MarcTheSpark/clockblocks`)
  + `sourcehut`, branches `main` + `playback_queue_attempt`.
- The two histories are **unrelated**. So "move cb2 into being the 1.0 of clockblocks" = (a) finish the work,
  then (b) graft cb2's content/history into the clockblocks repo. It is *not* `git branch 1.0`.

## Branching convention for a major bump (Marc's question)

Marc asked: "is the usual approach to duplicate into a new branch and work from there, leaving the old branch
for bug fixes?" — The standard convention is the **inverse**:

- New/major work continues on **`main`**; `main` *becomes* 1.0 and gets tagged `v1.0.0`.
- The **old line** gets a **maintenance branch** cut from the last 0.x release (e.g. `0.6.x`), and bug fixes
  are committed + tagged there (`v0.6.11`, ...).

Rationale: the major version is the future, so it lives on the default branch CI + new contributors target;
the old version is winding down, so it gets the named siding. You don't develop the new major on a side branch.

## The graft (preserve cb2's history)

Recommended path — unrelated-history merge so the redesign lineage (the cb2 commit log + `.claudeConvos/`
*is* the design record) survives:

1. `git -C clockblocks branch 0.6.x` (+ optional tag `v0.6.x-final`), push — the bug-fix siding.
2. `git -C clockblocks remote add cb2 ../cb2 && git -C clockblocks fetch cb2`; on a `1.0-dev` branch
   `git -C clockblocks merge --allow-unrelated-histories cb2/main`, **taking cb2's tree wholesale** (full
   replacement, not a real reconcile — the merge exists to staple histories together).
3. On `1.0-dev`: rewrite `~cb2.…` → `~clockblocks.…` xrefs, qualify bare cross-module xrefs, bump
   `pyproject.toml` → `1.0.0`, changelog.
4. Merge → `main`, tag `v1.0.0`, push to `origin` + `sourcehut`.

Simpler fallback if history doesn't matter: one "clockblocks 1.0 rewrite" commit copying cb2's tree over,
keep cb2 as an archive/tag. Loses step-by-step lineage. **Recommended: the merge.**

Phase 2 is outward-facing + hard to reverse (pushes to two public remotes) — don't start until the work is
finished and explicitly green-lit.

## Replacing mock_time: TimingBackend injection over monkeypatch (decided + built same day)

Follow-up to the above — Marc pushed on *how* to fix the dead `mock_time`. Worked through the options:

- **Why `mock_time` died:** it patched `time.time` + `threading.Event`. The redesigned scheduler reads
  `time.perf_counter` and blocks on a `Condition`, so the patches no longer reach it.
- **The key fact that makes this tractable:** there is **exactly one timed sleep in the whole family** —
  the scheduler's STEP 1c `_queue_change_condition.wait(timeout)` (two call sites). Everything else
  (`_wait_event`, `_scheduler_park_condition`, the empty-queue wait) blocks *untimed*, until notified. So
  "mock time" = control just two things: the time source (`perf_counter`) and that one timed block.
- **Why patching the Condition is unavoidable (not just `perf_counter`):** the Condition's `wait(timeout)`
  is the thing that *actually sleeps*, and it measures its timeout against real `monotonic` internally — you
  can't fool that by mocking `perf_counter`. Mock only `perf_counter` → scheduler *thinks* time flew but
  still really sleeps full-length (over-waits by the factor). Mock only the condition → the timing-policy
  "am I behind?" math is in a different domain and goes haywire. Need both, in one domain. Scaling the
  *timeout* (not replacing the block) preserves the essential early-wake-on-`notify()`.
- **Monkeypatch vs injection — I initially called the monkeypatch "less work" and was wrong** (Marc caught
  it). That was measuring first-commit lines, ignoring the monkeypatch's global blast radius (patches every
  `Condition`/`perf_counter` in-process), construction-order landmine, import-time start anchor, and that
  it's throwaway. The construction seam already existed (`ClockFamilyOptions` fields are forwarded one-by-one
  into `Scheduler(...)`), so injection is ~1 field + 1 forward + ~7 scheduler edits + 2 tiny classes.
- **Marc's refinement — `get_sleep_condition()` instead of a `scale(timeout)` hook — is the better shape,**
  and it's what we built. The backend hands back the very `Condition` the monkeypatch would have built, so
  the two **correctness-critical wait call sites stay byte-for-byte unchanged** (scaling lives inside the
  returned Condition subclass). The only "clunk" was a naming mismatch: that condition is *also* the family's
  heap mutex, so a thing called "time basis" handing it over felt wrong. Resolved by naming the abstraction
  for the role it actually plays — **`TimingBackend`** (a "now + the thing to block on" backend), not a clock.
- **Why this beats `scale()` long-term:** `scale()` can only rescale a duration; the PLAN's external-transport
  feature needs to *redefine waiting* ("unblock when the host clock reaches t, or on a notify"), which is a
  custom `Condition.wait`, not a rescaled number. So `get_sleep_condition()` is the same seam the transport
  driver will use — test mock and transport become two backends of one protocol. `scale()` would be thrown away.

**Built:** `TimingBackend` (default = real `perf_counter` + plain `Condition`) and `CompressedTime(factor)`
(scaled `now()` + a `Condition` whose `wait` divides the timeout) in `scheduler.py`; `Scheduler` takes a
`time_backend`; `ClockFamilyOptions.time_backend` forwards it; both exported from `cb2/__init__.py`.
`test_clock.py` converted to `CompressedTime(10)` (3 policy tests in ~0.4 s vs ~3.6 s real-time). `mock_time.py`
**deleted**. All 131 tests pass.

**The load-bearing caveat (in `CompressedTime`'s docstring + `tests/README.md`):** cross-thread handshakes
(scheduler↔clock park/wake) are real context switches and are **not** compressed, so a T-second wait costs
~`T/factor + handshake_overhead`. Large factors hit that floor and *loosen* achievable tolerances — which is
also exactly why a true zero-wait virtual clock is unsafe here (it'd reorder real concurrent forks). 10× is
the sweet spot. Reason in the scheduler's domain when writing compressed tests: off-clock delay of S
scheduler-seconds is `time.sleep(S/factor)`, observed wake = `real_elapsed * factor`.

## Suite-wide compression knob (added same day)

Follow-up ask: make the *whole* suite respond to a single compression argument, not just `test_clock`.

- **Mechanism (cheap):** `scheduler.py` got a neutral `_default_time_backend()` factory (`Scheduler.__init__`
  uses `time_backend or _default_time_backend()`). `tests/__init__.py` reads env var `CB2_TEST_COMPRESSION`
  (default 1) and, when set, repoints that factory at `CompressedTime(factor)` — so every Clock/Scheduler the
  suite builds (both construction paths: `Clock(...)`→Scheduler, and direct `Scheduler(...)`) runs compressed
  with **zero per-test construction changes**. `tests/timing.py` holds `FACTOR` + the domain helpers
  (`stopwatch`/`elapsed`/`sleep`). Env var, not a unittest CLI flag — unittest owns argv parsing.
- **The actual work was the per-test discipline, not the plumbing.** ~28 assertions across 10 files compared
  *real* wall time to *scheduler*-time values (correct only at factor 1). Each moved into the scheduler
  domain: `start=time.time()`→`timing.stopwatch()`, `time.time()-start`→`timing.elapsed(start)` (= real×F),
  and any off-clock `time.sleep(S)` that the scheduler *perceives* or that gets *measured* →
  `timing.sleep(S)` (= real S/F). The subtle ones: (a) a real sleep inside a scheduler action is perceived
  as `S×F` scheduler-seconds, so action-work sleeps in `test_scheduler._test_timing_policy` had to convert or
  the timing-policy math breaks; (b) `test_scheduler`'s "let the scheduler peek" 0.2 s sleep, once measured,
  became `0.2×F` and blew the `<1.0` bound until converted; (c) `test_fast_forward`'s poke
  `threading.Timer(2.0)` had to become `2.0/FACTOR` to land in the (shrunken) post-goal tail. A real sleep
  that's *only* a behavior gate and never measured (e.g. `test_while_quiescent`'s action sleep) was left real.
- **Regression check:** at FACTOR=1 the helpers are identities, so all 139 must pass unchanged — they do.
  At 10× the suite drops ~50 s → ~7 s, 5 skips. **Tolerances:** `test_scheduler`'s tight `delta=0.01` scales
  linearly (`×FACTOR`); `test_clock`'s already-loose `0.08` only widens above 10× (`×max(1, F/10)`) — 20×
  then passes too. Beyond ~20× the timing-policy tests get flaky (the handshake floor) — documented ceiling,
  not a bug.
- **Pinned real-time:** scheduler-level precise-timing tests + "default backend is real"
  `@skipUnless(timing.FACTOR == 1)` — compressing a precision test is meaningless, and the global override
  deliberately changes that default.
